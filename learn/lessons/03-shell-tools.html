03. The tools Xcode is hiding from you

When you hit Run in Xcode, a dozen command-line tools fire off in sequence. memwatch doesn't have an Xcode to hide behind — it calls those same tools directly. Here's what each one does.

The simulator is a regular process on your Mac

Critical mental model shift: the iOS Simulator is not a virtual machine. It's a regular Mac process tree. The iOS frameworks (UIKit, SceneKit, etc.) are reimplemented to run natively on macOS. When you run your app on the iPhone 15 simulator, your app's binary is an x86-64 or arm64 Mach-O executable running on your Mac, with a regular Mac PID, talking to the same kernel as Safari and Slack.

That's why memwatch can attach to it with heap and leaks — those are standard Mach-process tools that work on any Mac process. If your app actually ran on a simulated ARM CPU inside a hypervisor, none of this would work.

Mach is the kernel core macOS is built on (plus a BSD layer on top). Tools like heap, leaks, vmmap, and sample use Mach APIs (task_for_pid, virtual memory introspection) to inspect a running process's memory without its cooperation. You don't have to add anything to your app for them to work.

xcrun: the toolchain umbrella

You have multiple Xcode versions, multiple toolchains, multiple SDKs. xcrun is the dispatcher that finds the right binary for the current developer dir. You can call most tools both with and without it — heap, leaks, and simctl are all on PATH after Command Line Tools are installed — but going through xcrun is the convention because it picks the version matching your active Xcode.

xcrun --find heap tells you which binary it would invoke. xcrun --sdk iphonesimulator --find clang would point at the simulator-targeting clang. Switch between Xcodes with sudo xcode-select -s /Applications/Xcode-beta.app.

simctl: drive the simulator from the command line

xcrun simctl is your handle to the simulator from outside Xcode. The subcommands you'll care about for memwatch: 

$ xcrun simctl list devices booted -j
{
  "devices" : {
    "com.apple.CoreSimulator.SimRuntime.iOS-17-2" : [
      {
        "udid" : "1A2B3C4D-...",
        "state" : "Booted",
        "name" : "iPhone 15"
      }
    ]
  }
}

list devices booted -j returns JSON describing every booted simulator. Parsing the first udid out of this is how memwatch gets the simulator handle when you don't pass --simulator.

Other commands you'll see:

  • simctl boot <udid> — boot a sim that's shut down
  • simctl launch <udid> <bundle-id> — start your app on the sim, returns its PID
  • simctl get_app_container <udid> <bundle-id> — find the app's filesystem sandbox
  • simctl listapps <udid> — every app installed on that sim, by bundle id
A process identifier — a small integer assigned by the kernel to each running process. This is how every other tool in this lesson references the target: heap 49281, leaks 49281. memwatch's job before running any introspection tool is "translate this bundle id into a PID."

heap: every live allocation, by class

The headline tool. Given a PID, heap walks every malloc zone in that process and emits a per-class summary of every live allocation: how many instances exist and how much memory they collectively use.

An allocator-internal grouping of allocations. The default zone holds most of your normal allocations; specialized zones hold things like CoreFoundation strings or specific framework caches. heap reports them separately but the summary table aggregates by class regardless of zone.

The summary table — the part memwatch parses — looks like this:

Process 49281: 2,847 nodes malloced for 8,124 KB

       COUNT    BYTES  AVG   CLASS_NAME
       =====    =====  ===   ==========
         482  983,040  2.0K  CFString
         247  198,400  812   SCNNode
         187   12,016  64    UIView
         154    9,856  64    NSConcreteMutableData
          18   89,344  4.9K  SCNGeometry
          12  124,928  10.2K GhostController
           ...

That's the parseable signal. Per row: count, bytes, average, class name. memwatch's HeapParser reads this table line-by-line and emits a [HeapClassEntry]. Header lines and zone breakdowns get skipped — anything that doesn't match the four-column pattern is ignored silently because Apple has changed the surrounding text between Xcode releases and the contract is "skip noise, never crash."

Then a snapshot taken later is just another [HeapClassEntry], and the diff is per-class subtraction on count and bytes. That's the entire pipeline.

leaks: definitively-orphaned blocks

Where heap shows everything that's alive, leaks shows specifically the allocations that nothing points at — they're live in memory but no reference graph node anywhere reaches them. That's a strict superset of "buggy" but a strict subset of "wrong" — a retain cycle leak isn't reported by leaks because each object in the cycle is referenced (by the other one). heap diff catches retain cycles; leaks catches abandoned allocations.

leaks output is more verbose — full call stacks, malloc histories. It's slow (it walks the entire reference graph to determine reachability). memwatch keeps it as an on-demand tool exposed over MCP, not part of the snapshot path.

swift-demangle: turning $s5... into something a human can read

Swift symbols in the binary look like $s7MyApp14GhostControllerC4tickyyF. That's a deterministic encoding of MyApp.GhostController.tick() (module, type, method, signature). The compiler produces those names; tools that walk the binary see them. swift-demangle reverses the mapping.

$ echo '$s7MyApp14GhostControllerC4tickyyF' | xcrun swift-demangle prints MyApp.GhostController.tick() -> (). Pipe-friendly, supports both line-by-line and inline-substitution modes.

heap's class names from a Swift app are sometimes already demangled, sometimes not — depends on the metadata. memwatch shells out to xcrun swift-demangle when it sees a mangled name. There's no public Swift library API for demangling, so shelling out is the supported path.

How Swift shells out: Process and Pipe

Foundation ships Process, the Swift wrapper for fork+exec. You configure executable, arguments, environment, then attach Pipes to capture stdout/stderr.

Same Foundation type that's been there since OpenStep, just renamed from NSTask. macOS-only-ish (Process exists on Linux but the spawning semantics differ slightly). Async-friendly via Swift Concurrency: you can await the child to terminate without spinning a thread.

memwatch wraps this in a Shell helper with one method: run(_ cmd: String, _ args: [String]) async throws -> (stdout: String, stderr: String, exitCode: Int32). Every shell-out goes through it, so the simulator-resolution path, the heap path, and the leaks path share one well-tested code path.

That's exactly why heap, leaks, etc. — generic Mach-process tools — work against it.
2. Which signal does the diff between two heap snapshots catch that leaks would miss?
leaks reports unreachable allocations. Retain cycles are reachable from one another, so they're not unreachable — but they're still wrong, and they show up as a positive count delta on the round-trip heap diff.
3. Why does memwatch shell out to xcrun swift-demangle instead of importing a demangle library?
There's a private Swift module that contains demangling code, but it's not stable and not exported. The binary is what Apple commits to.
