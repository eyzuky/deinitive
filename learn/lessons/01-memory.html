01. iOS memory: heap, leak, diff

You already know ARC and weak. This lesson reframes those for the question a profiler asks: what's still alive that shouldn't be?

Heap growth is not a leak

The heap is the region of process memory where reference-counted objects live. Every UIView, every SCNNode, every NSMutableData — they're all on the heap. ARC increments a refcount when you assign a strong reference and decrements when that reference goes out of scope. When the count hits zero, the object is freed.

Automatic Reference Counting. The compiler inserts retain/release calls around your code so you don't have to manage memory by hand. It's still refcounting under the hood — there's no garbage collector running. Each object knows its own count.

So when your app's heap grows, that's not by itself a problem. The user navigated into a level → 247 SceneKit nodes loaded → heap grew 200 KB. That's the level loading. Expected.

A leak is something else: an object whose refcount should have hit zero, but didn't, because something is still holding a strong reference to it. The user navigated back from the level — but the 247 nodes are still alive in memory, costing you 200 KB you'll never reclaim.

The canonical leak: navigate-and-back

Almost every leak you'll hunt in a production iOS app fits this shape: 

1. user is on screen A
2. user navigates to screen B (allocates objects)
3. user navigates back to screen A
4. you expect screen B's objects to be freed
5. some are not — that's the leak

The classic cause is a retain cycle: two objects holding strong references to each other. Neither's refcount can ever drop to zero, so ARC never frees them.

The compiler can't detect cycles for you because at compile time it can't know which references are "owning." That's why [weak self] in closures and weak var delegate on protocols are conventions you apply manually.

Why diffing snapshots is the right unit

You can't see a leak from one heap snapshot. A snapshot of "after navigating into a level" shows 247 SceneKit nodes — fine, that's the level. The question is: after I navigate back, are they still there?

That's why memwatch's primary verb is diff, not snapshot. The snapshot is the raw input; the diff is the answer. Here's the mental model: 

   menu          level1         menu (after)
     │             │                  │
     ├─snapshot ───┤                  │
     │   "menu"    │                  │
     │             ├──snapshot ───────┤
     │             │   "level1"       │
     │             │                  ├──snapshot ─→
     │             │                  │   "back"
     │             │                  │
     └─────────────┴──diff menu back──┘
                       (← any positive Δ here is a leak)

The diff between menu and back is the round-trip residue. Anything with a positive count delta there is something the round trip allocated and never released. The diff between menu and level1 is just "what loading the level cost" — interesting, but not a bug signal.

In the canonical workflow you take three snapshots: at the menu, at the deepest screen you navigated to, and back at the menu. The first→third diff is the leak signal. The first→second diff is the working set of the visited screen.

What the heap tool sees that you can't from inside the app

From inside your app, you can ask "is this object still alive" only by holding a reference to it — which itself keeps it alive. You're inside the system you're trying to measure.

From outside, the heap <pid> tool walks every malloc zone in the target process and reports every live allocation: classified by class, with counts and total bytes. It sees what your app can't see about itself: the actual graph of live objects, including the ones nothing in your code remembers anymore but that something else is still pinning.

That's what the next two lessons get into: how the simulator is a separate process you can attach tools to (lesson 3), and how memwatch composes those tools into a one-line workflow (lesson 2 sets up the Swift CLI plumbing).

quiz — 3 questions

1. ARC frees an object when:
Refcount reaching zero is the trigger; deinit is what runs because of it, not what causes it.
2. You snapshot menu (count: 100), navigate to a level and snapshot level (count: 250), then navigate back and snapshot back (count: 150). Which is true?
The 50-object delta between menu and back is the round-trip residue. It might be expected (e.g., a cache pre-warmed) but it's the right place to look.
3. Why is positive heap growth between two snapshots not always a leak?
A senior dev reading the diff judges whether each ΔClass is expected. memwatch shows the data; you decide what's a leak.
