04. JSON-RPC, MCP, and the big picture

memwatch's CLI is the foreground product. The MCP server is the multiplier — it lets an AI coding agent see what your app sees about itself. Here's the wire protocol and why it matters.

JSON-RPC 2.0: a tiny RPC encoding

JSON-RPC is a 9-page RPC protocol that says: the client sends a JSON object describing a method call, the server sends back a JSON object describing the result. That's it. No HTTP. No URLs. No verbs. Just message exchange.

Remote Procedure Call — the umbrella for "make a function call across a process boundary." gRPC, JSON-RPC, XML-RPC, OpenAPI/REST when used as an RPC, MCP — all variations on the same idea.

A request:

{ "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": { "name": "memwatch_diff", "arguments": { "before": "menu", "after": "level1" } } }

A response:

{ "jsonrpc": "2.0", "id": 7,
  "result": { "content": [{ "type": "text", "text": "ClassName ΔCount ΔBytes\nSCNNode +247 +198KB ..." }] } }

Three rules carry essentially the entire protocol:

  • Every message has "jsonrpc": "2.0".
  • Every request has an id (any string or number); the response carries the same id so clients can match them up.
  • Messages without an id are notifications — fire-and-forget; the server doesn't reply. Useful for "I'm ready" / "I'm done" / "log this" signals.

Errors look like { "jsonrpc": "2.0", "id": 7, "error": { "code": -32601, "message": "Method not found" } }. The error codes are standardized.

-32700 Parse error · -32600 Invalid Request · -32601 Method not found · -32602 Invalid params · -32603 Internal error. Application-defined errors live in -32000 to -32099.

Stdio framing: newline-delimited JSON

JSON-RPC says nothing about transport. MCP picks one: each message is a single line of JSON, terminated by \n, written to the server's stdin; replies come out of stdout the same way. Logs and warnings go to stderr — and only stderr, because any byte of non-JSON on stdout corrupts the protocol. Print a debug line to stdout in an MCP server and the client throws a parse error.

That's why memwatch mcp's spec says "log to stderr ONLY." It's not a stylistic choice; stdout is the wire.

Why an agent launches memwatch over stdio

Cursor, Claude Code, and similar agents follow a config file (e.g. ~/.cursor/mcp.json): 

{
  "mcpServers": {
    "memwatch": {
      "command": "/usr/local/bin/memwatch",
      "args": ["mcp", "--bundle", "com.eyalg.GhostMaze"]
    }
  }
}

When the agent starts, it spawns each configured server as a child process, hooks up stdin/stdout/stderr, and runs the JSON-RPC handshake. From that point on, the agent can call any tool the server advertises.

memwatch's four MCP tools

The server advertises these in tools/list; each maps to a function in MemwatchCore:

  • memwatch_snapshot(tag, bundle) — capture and persist, returns summary
  • memwatch_diff(before, after) — compute and return the diff table as text
  • memwatch_current(bundle) — top-20 allocators right now, no persistence
  • memwatch_leaks(bundle) — run leaks and return parsed summary + raw output

Each tool maps to a JSON Schema in tools/list so the agent knows what arguments are valid. Argument validation happens client-side (the agent won't pass unknown fields) but the server still validates because nothing prevents a malformed call.

The big picture: why the agent + memwatch is more than either alone

An AI coding agent has access to your entire source tree. It can see GhostController.swift's closures, read every weak annotation, follow your navigation graph through code. What it cannot see is what's actually live in memory right now. Static analysis can suspect a retain cycle; only runtime data can confirm it.

memwatch alone gives a human the heap diff but stops at presentation. The human still has to map "247 SCNNodes leaked" back to "which closure in GhostController.swift." That's the boring detective work.

Combine them — agent has source, memwatch has heap, both in one conversation — and the loop closes: 

YOU:    take a snapshot tagged 'menu'
AGENT:  → memwatch_snapshot { tag: "menu" }
        ✓ saved snapshot 'menu' (pid 49281, 1247 classes)

YOU:    [navigate into level 1, then back to menu]
        diff menu against now

AGENT:  → memwatch_snapshot { tag: "back" }
        → memwatch_diff { before: "menu", after: "back" }
        I see SCNNode +12, GhostController +1, SCNGeometry +18 between
        the two snapshots. Looking at GhostController.swift:84, the
        completion block on `loadGhosts` captures `self` strongly.
        Adding [weak self] would break the retain cycle. Want me to?

YOU:    yes

That's it. That's why memwatch ships an MCP server even though the diff workflow is already great as a CLI for humans. The MCP layer turns memwatch from a tool into a sense organ for an agent that already has eyes for code.

quiz — 3 questions

1. JSON-RPC distinguishes a request (expects a reply) from a notification (no reply) by:
No id = no reply expected. The notifications/ prefix is an MCP convention but the wire-level distinction is whether id is present.
2. Why must memwatch mcp's logs go to stderr, never stdout?
The client expects every line on stdout to be a valid JSON-RPC message. A stray print("hello") = client-side parse error and a broken connection.
3. The unique value of memwatch-as-MCP-server (vs. memwatch-as-CLI alone) is:
Static analysis suspects retain cycles; only runtime data confirms one. memwatch supplies the runtime side; the agent supplies the static side.
