02. Swift CLIs and SPM

If you've only ever opened .xcodeproj files, this is the gap that closes here. Swift can absolutely live without Xcode — and on the command line, that's the only sensible way.

Swift Package Manager is a build system, not just a dependency manager

In an iOS app you usually use SPM through Xcode — File → Add Packages, and a third-party library shows up. That's a small fraction of what SPM does. SPM is a full, standalone build system. With one file (Package.swift) and a directory layout, it can build executables, libraries, and tests, with no Xcode involved.

memwatch is built this way. There is no .xcodeproj. The CLI you're going to ship is produced by swift build -c release straight from a Package.swift manifest.

The manifest is itself a Swift file — at the top is // swift-tools-version: 5.10, which tells SPM which compiler to interpret it with. The file imports PackageDescription and constructs a Package value. SPM evaluates this file before building anything else.

Anatomy of memwatch's Package.swift

This is your actual manifest, annotated. Click any underlined term:

// swift-tools-version: 5.10
import PackageDescription

let package = Package(
    name: "memwatch",
    platforms: [.macOS(.v14)],
    products: [
        .executable(name: "memwatch", targets: ["memwatch"]),
        .library(name: "MemwatchCore", targets: ["MemwatchCore"]),
        .library(name: "MemwatchMCP", targets: ["MemwatchMCP"]),
    ],
    dependencies: [
        .package(url: "https://github.com/apple/swift-argument-parser.git", from: "1.5.0"),
    ],
    targets: [
        .executableTarget(
            name: "memwatch",
            dependencies: [
                "MemwatchCore",
                "MemwatchMCP",
                .product(name: "ArgumentParser", package: "swift-argument-parser"),
            ]
        ),
        .target(name: "MemwatchCore"),
        .target(name: "MemwatchMCP", dependencies: ["MemwatchCore"]),
    ]
)
products are the things the package builds and exposes to the outside world. .executable produces a runnable binary; .library produces a static or dynamic library that another package could link. memwatch is one executable plus two libraries that the executable consumes.
targets are the actual compilation units. Each target maps to a directory under Sources/ by default — a target named memwatch reads Sources/memwatch/. Targets list dependencies on other targets in the package or on external products from dependencies.
.executableTarget vs plain .target is the meaningful distinction: only .executableTarget produces a binary with an entry point (a main function). Library targets do not, and trying to put a @main in one is an error. The executable depends on the libraries; the libraries don't depend on each other beyond what's declared.

Where does main() live?

Look at Sources/memwatch/Memwatch.swift in your repo: 

@main
struct Memwatch: AsyncParsableCommand {
    static let configuration = CommandConfiguration(
        commandName: "memwatch",
        abstract: "snapshot and diff iOS simulator heap state",
        subcommands: [Snapshot.self, Diff.self, List.self, Clear.self, MCP.self]
    )
}

No func main(). No main.swift. The @main attribute does it. AsyncParsableCommand ships a static func main() async that the attribute hooks into; the program's actual entry point becomes "parse argv, dispatch to the matching subcommand, run it."

@main is a Swift language attribute, not a swift-argument-parser thing. It marks one type as the program's entry point, expecting a static func main() on it. The async variant exists because Swift's top-level entry now supports awaiting tasks.

Each subcommand is its own struct. Here's Snapshot, simplified: 

struct Snapshot: AsyncParsableCommand {
    static let configuration = CommandConfiguration(
        commandName: "snapshot",
        abstract: "capture heap state and tag it"
    )

    @Option(name: .shortAndLong) var tag: String
    @Option(name: .shortAndLong) var bundle: String
    @Option(name: .shortAndLong) var simulator: String?

    func run() async throws {
        // here be the real logic, in Phase 2c
    }
}

@Option declares a flag that takes a value (--tag foo). @Argument would declare a positional. @Flag declares a boolean (--yes). swift-argument-parser uses these property wrappers + reflection to generate help text, parse argv, validate types, and call your run().

Why async throws on run()?

Two reasons:

  • throws — any error you throw from run() propagates out as a non-zero exit code. You don't write your own error-handling top level. Errors that conform to LocalizedError get printed nicely.
  • async — memwatch is going to spawn child processes (heap, leaks, xcrun) and read their output streams. Async lets you await the child to finish without blocking a thread.
Same Swift Concurrency you use in apps. async/await, Task, structured concurrency. The CLI runtime gives you a top-level async context for free; you just write func run() async throws and you can await inside.

Why three targets?

memwatch has three Sources directories: the memwatch executable, MemwatchCore library, and MemwatchMCP library. Why split it?

The executable target should own only the CLI surface: argument parsing, subcommand dispatch, printing. Everything domain-y — running the heap tool, parsing its output, modeling a snapshot, computing a diff — lives in MemwatchCore. That makes MemwatchCore trivially testable: tests link against the library directly without going through argv, the file system, or a child process.

MemwatchMCP is a separate library because the MCP server is a different consumer of the same core. The CLI calls SnapshotStore.save(...); the MCP server, when handling a tools/call request, calls the same function. Splitting MCP into its own library means you could imagine someone using MemwatchMCP from a different Swift host one day — but the more immediate value is just clean separation of concerns.

quiz — 3 questions

1. What does .executableTarget(...) do that plain .target(...) doesn't?
A library target compiles to a static archive with no main. .executableTarget is the one that lets you put @main on a type.
2. memwatch has no main.swift and no explicit main() function. What runs first when you execute the binary?
@main is the language feature; AsyncParsableCommand provides the static main() implementation that @main calls.
3. After swift build -c release succeeds, the binary ships from:
SPM never installs anything globally. The release binary is a single self-contained file in .build/release/; you copy it wherever you want it on PATH.
